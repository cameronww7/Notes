## Core Concepts

**Term: Microservices** **Definition:** Breaking one application into small, independent services that each do one job and can be built, deployed, and scaled separately. **Problem it solves:** One team can't ship changes without waiting on or breaking everyone else's code in a giant shared codebase. **When it's the WRONG choice:** Small teams or early-stage products. You'll spend more time managing network calls, deployments, and monitoring across services than you would just building one solid app. Most "microservices too early" stories end in the team quietly going back to a monolith.

**Term: Serverless** **Definition:** A model where you deploy code and the cloud provider handles provisioning, scaling, and running the servers behind it. **Problem it solves:** Paying for and managing servers that sit idle most of the time, or manually scaling infrastructure for unpredictable traffic. **When it's the WRONG choice:** Long-running or steady, high-volume workloads. Cold starts add latency, and at consistent high scale, serverless often costs more than a fixed set of servers you manage yourself.

**Term: K8s (Kubernetes)** **Definition:** A system that automates deploying, scaling, and managing containers across a cluster of machines. **Problem it solves:** Manually starting, restarting, and load-balancing containers across servers as things fail or traffic changes. **When it's the WRONG choice:** A small app or small team. Kubernetes has a steep learning curve and real operational overhead. If you're running a handful of services, it's often overkill compared to a simpler platform like a managed container service.

**Term: Backend** **Definition:** The server-side part of an application: databases, business logic, and APIs that the user doesn't directly see. **Problem it solves:** Sensitive logic and data can't live in the user's browser or device where it could be read or tampered with. **When it's the WRONG choice:** N/A as a concept, nearly all real applications need one. The "wrong choice" question here is really about how much backend you build versus using managed/backend-as-a-service tools.

**Term: Middleware** **Definition:** Code that intercepts requests between two systems to perform a shared task, like authentication, logging, or formatting, before passing the request along. **Problem it solves:** Repeating the same logic (auth checks, logging) in every single service or route instead of handling it once, centrally. **When it's the WRONG choice:** When overused for business logic instead of cross-cutting concerns. Stacking too much middleware makes requests slow and hard to debug because you can't easily see what's touching the request along the way.

**Term: Mobile** **Definition:** Apps built specifically for phones and tablets, following each platform's rules for UI, offline behavior, and app store distribution. **Problem it solves:** Desktop-built websites and apps don't work well on small screens, touch input, or intermittent connectivity. **When it's the WRONG choice:** When your users primarily work at a desk and don't need a native app. A responsive web app is cheaper to build and maintain than two separate native mobile apps.

## Containers and Orchestration

**Term: Container** **Definition:** A packaged bundle of an app plus everything it needs to run (dependencies, config), so it behaves the same on any machine. **Problem it solves:** "It works on my machine" but breaks in production because of differences in environment. **When it's the WRONG choice:** Simple scripts or single-server apps with no scaling or portability needs. Containers add setup overhead that isn't worth it for a one-off tool.

**Term: Orchestration** **Definition:** Automated management of many containers: where they run, how they scale, and how they recover from failure. **Problem it solves:** Manually tracking and restarting containers across multiple servers as load or failures change. **When it's the WRONG choice:** Running just a few containers on one or two servers. Docker Compose or a simple managed service does the job without the complexity of a full orchestrator.

**Term: Docker** **Definition:** The most widely used tool for building, packaging, and running containers. **Problem it solves:** Inconsistent environments between development, testing, and production. **When it's the WRONG choice:** Rarely wrong on its own, but not a fit for workloads needing bare-metal performance or direct hardware access, where the container layer adds unnecessary overhead.

**Term: Helm** **Definition:** A package manager for Kubernetes that bundles configuration into reusable, versioned templates ("charts"). **Problem it solves:** Copy-pasting and hand-editing raw Kubernetes YAML files for every deployment and environment. **When it's the WRONG choice:** Very simple Kubernetes setups with one or two static deployments. Helm's templating adds a layer of abstraction that can obscure what's actually being deployed.

**Term: Pod** **Definition:** The smallest deployable unit in Kubernetes, usually a single container or a tightly coupled group of them. **Problem it solves:** Kubernetes needs an atomic unit to schedule and scale, rather than managing raw containers directly. **When it's the WRONG choice:** N/A, it's the base building block if you're using Kubernetes at all.

**Term: Namespace** **Definition:** A way to logically divide a single Kubernetes cluster into isolated sections. **Problem it solves:** Multiple teams or environments (dev, staging, prod) sharing one cluster and colliding on resource names or access. **When it's the WRONG choice:** When you actually need hard security isolation. Namespaces are a soft boundary, not a security boundary, use separate clusters if workloads shouldn't be able to reach each other at all.

**Term: ConfigMap** **Definition:** A Kubernetes object for storing non-sensitive configuration data separately from application code. **Problem it solves:** Hardcoding settings into your app image, meaning any config change requires a rebuild. **When it's the WRONG choice:** Storing secrets. ConfigMaps are not encrypted at rest by default, sensitive values belong in a Secret or a dedicated secrets manager instead.

**Term: Secrets Management** **Definition:** A secure system for storing and distributing credentials, API keys, and certificates, separate from application code. **Problem it solves:** Passwords and keys hardcoded in source code or config files, where anyone with repo access can read them. **When it's the WRONG choice:** It's rarely wrong to use one, the mistake is skipping it for "just this one quick script," which is exactly how credentials end up leaked in a public repo.

**Term: Sidecar** **Definition:** A helper container that runs alongside a main application container in the same pod, handling a supporting task like logging or traffic proxying. **Problem it solves:** Building the same cross-cutting functionality (like TLS handling or log shipping) into every single service's codebase. **When it's the WRONG choice:** Latency-sensitive workloads where the extra network hop through the sidecar matters, or small deployments where the added resource overhead per pod isn't worth the operational benefit.

## Networking and Traffic

**Term: API Gateway** **Definition:** A single entry point that routes, authenticates, and manages incoming requests before they reach backend services. **Problem it solves:** Every microservice having to implement its own auth, rate limiting, and routing logic separately. **When it's the WRONG choice:** A single monolithic backend with one entry point already. Adding a gateway there just adds latency and a new point of failure for no real benefit.

**Term: Load Balancer** **Definition:** A component that distributes incoming traffic across multiple servers or instances. **Problem it solves:** One server getting overwhelmed while others sit idle. **When it's the WRONG choice:** A single-instance app with predictable, low traffic. It's added infrastructure and cost with no upside until you actually need redundancy or scale.

**Term: Service Mesh** **Definition:** A dedicated infrastructure layer that handles service-to-service communication: security, retries, traffic control, and observability. **Problem it solves:** Each microservice reimplementing retries, encryption, and monitoring logic on its own, inconsistently. **When it's the WRONG choice:** Fewer than roughly a dozen services. A service mesh (like Istio) adds real operational complexity and latency that isn't justified until you have enough services to make manual coordination painful.

**Term: Istio / Envoy** **Definition:** Envoy is a high-performance proxy that handles the actual traffic between services. Istio is a control layer that configures and manages a fleet of Envoy proxies. **Problem it solves:** Manually configuring encryption, retries, and traffic rules service-by-service. **When it's the WRONG choice:** Small clusters or teams without dedicated platform engineering. Istio in particular has a reputation for being heavy to operate and debug.

**Term: Ingress** **Definition:** A Kubernetes resource that manages external HTTP/HTTPS traffic routing into the cluster. **Problem it solves:** Exposing many internal services to the outside world without giving each one its own public load balancer. **When it's the WRONG choice:** Non-HTTP traffic (like raw TCP or UDP), where Ingress doesn't apply and you need a different service type (like LoadBalancer or NodePort).

**Term: Reverse Proxy** **Definition:** A server that sits in front of backend servers and forwards client requests to them, hiding the backend's details. **Problem it solves:** Exposing internal servers directly to the internet, which increases attack surface and makes scaling/routing harder. **When it's the WRONG choice:** Extremely simple, single-server setups where the added hop isn't buying you security or routing benefits yet.

**Term: Circuit Breaker** **Definition:** A pattern that stops sending requests to a failing service temporarily, preventing cascading failures. **Problem it solves:** One failing service causing a chain reaction that takes down the whole system. **When it's the WRONG choice:** Non-critical, low-stakes internal calls where a simple retry or timeout is enough, adding circuit breaker logic everywhere increases complexity without meaningful benefit.

**Term: Rate Limiting** **Definition:** Restricting how many requests a client can make in a given time window. **Problem it solves:** A single user, bot, or bug hammering your API and degrading service for everyone else. **When it's the WRONG choice:** Rarely wrong to have some, but limits set too aggressively can block legitimate traffic and burst usage, tune based on real patterns, not guesses.

**Term: mTLS (mutual TLS)** **Definition:** A protocol where both the client and server verify each other's identity via certificates before communicating. **Problem it solves:** A compromised or spoofed service impersonating a legitimate one inside your network. **When it's the WRONG choice:** Low-sensitivity internal traffic where the certificate management overhead outweighs the risk, though this bar is lower than most teams think.

**Term: Zero Trust** **Definition:** A security model where no user, device, or service is trusted by default, everything must authenticate and be authorized on every request. **Problem it solves:** Traditional "trusted internal network" models, where anyone who gets past the perimeter has broad access. **When it's the WRONG choice:** It's a direction, not a switch, jumping straight to full zero trust without the identity and access infrastructure to support it usually just creates friction without real security gain. Needs to be phased in.

## Communication Between Services

**Term: gRPC** **Definition:** A high-performance protocol for service-to-service communication using a compact binary format and strict contracts. **Problem it solves:** REST/JSON being too slow or too loosely defined for high-throughput, low-latency internal communication. **When it's the WRONG choice:** Public-facing APIs or browser clients. gRPC isn't natively browser-friendly and is harder to debug/inspect than REST, better suited for internal service-to-service calls.

**Term: REST** **Definition:** An architectural style for APIs using standard HTTP methods and predictable, resource-based URLs. **Problem it solves:** Needing a simple, widely understood, tool-friendly way for different systems to talk over HTTP. **When it's the WRONG choice:** High-frequency internal service calls where performance matters more than simplicity, or when the client needs flexible, nested data (GraphQL fits better there).

**Term: GraphQL** **Definition:** A query language that lets clients request exactly the data fields they need in a single call. **Problem it solves:** REST APIs requiring multiple round trips or over-fetching unnecessary data to assemble one screen's worth of information. **When it's the WRONG choice:** Simple APIs with predictable, fixed data needs. GraphQL adds real complexity (schema design, caching, security around query depth) that isn't worth it for basic CRUD.

**Term: WebSocket** **Definition:** A protocol that keeps a persistent, two-way connection open between client and server. **Problem it solves:** Constantly polling a server to check for updates, wasting requests and adding delay. **When it's the WRONG choice:** Anything that doesn't need real-time updates. Persistent connections cost more server resources than simple request/response, don't use it just because it's available.

**Term: Message Queue** **Definition:** A system that holds messages or tasks so they can be processed asynchronously, in order, even if the receiver is slower than the sender. **Problem it solves:** A fast producer overwhelming a slower consumer, or losing tasks if a service is briefly down. **When it's the WRONG choice:** Operations that need an immediate response, like a user waiting on a page load. Queues are for async work, not synchronous request/response.

**Term: Kafka / RabbitMQ** **Definition:** Kafka is a distributed system for handling continuous, high-volume streams of events. RabbitMQ is a traditional message broker for routing discrete tasks/messages. **Problem it solves:** Kafka: needing to process and replay massive event streams (like clickstream data). RabbitMQ: reliably routing individual jobs between services. **When it's the WRONG choice:** Kafka for simple task queues, it's overkill and operationally heavy for low-volume, simple job processing. RabbitMQ for huge, replayable event streams, it's not built for that scale or pattern.

**Term: Pub/Sub (Publish/Subscribe)** **Definition:** A messaging pattern where publishers send events without knowing who, if anyone, is listening, and subscribers receive events they care about. **Problem it solves:** Services being tightly coupled, where a publisher has to know every consumer directly. **When it's the WRONG choice:** When you need guaranteed processing order or a direct response, pub/sub is fire-and-forget by nature, not built for that.

**Term: Event-Driven** **Definition:** An architecture where actions trigger events, and other services react to those events independently. **Problem it solves:** Systems tightly chained together through direct calls, where one slow or failing service blocks everything downstream. **When it's the WRONG choice:** Simple, linear workflows where a direct function call is clearer. Event-driven systems are harder to trace and debug, don't add that complexity without a real need for decoupling.

## Auth and Access

**Term: Auth (OAuth/JWT)** **Definition:** OAuth is a standard for delegated login (like "Sign in with Google"). JWT is a signed token that proves identity without a database lookup on every request. **Problem it solves:** Building and securing your own login system from scratch, or re-verifying credentials on every single request. **When it's the WRONG choice:** JWTs for sessions that need to be instantly revocable, once issued, a JWT is valid until it expires unless you build extra infrastructure to revoke it early.

**Term: RBAC (Role-Based Access Control)** **Definition:** An access model where permissions are tied to roles (like "admin" or "editor") rather than individual users. **Problem it solves:** Managing permissions one user at a time, which doesn't scale and gets inconsistent fast. **When it's the WRONG choice:** Situations needing fine-grained, contextual permissions (like "this user can edit this specific record they own"), where attribute-based access control fits better than fixed roles.

## Scaling and Deployment

**Term: Horizontal Scaling** **Definition:** Adding more machines/instances to handle increased load, rather than making one machine more powerful. **Problem it solves:** A single server hitting its capacity ceiling under growing traffic. **When it's the WRONG choice:** Workloads that can't be easily distributed, like a single-threaded process with shared state, where vertical scaling (a bigger machine) may be simpler and cheaper.

**Term: Auto-scaling** **Definition:** Automatically adjusting the number of running instances based on real-time demand. **Problem it solves:** Manually adding or removing capacity for predictable or spiky traffic, or over-provisioning "just in case." **When it's the WRONG choice:** Workloads with very steady, predictable load, fixed capacity planning can be simpler and avoid the complexity of scaling logic and thresholds.

**Term: Cold Start** **Definition:** The delay before a serverless function or container is ready to handle a request because it wasn't already running. **Problem it solves:** N/A, this is a tradeoff/limitation of serverless, not a solution. **When it's the WRONG choice:** N/A as a concept. The relevant decision is avoiding serverless for latency-critical paths where cold starts would hurt user experience.

**Term: Multi-tenant** **Definition:** A single system architecture serving multiple customers, with their data logically separated. **Problem it solves:** Running and maintaining a separate full deployment for every single customer, which doesn't scale operationally. **When it's the WRONG choice:** Customers with strict regulatory or data isolation requirements that demand physically separate infrastructure, healthcare and government clients often require single-tenant.

**Term: Blue-Green Deployment** **Definition:** Running two identical environments, sending live traffic to one while deploying updates to the other, then switching over instantly. **Problem it solves:** Downtime and risk during deployments, and the difficulty of quickly rolling back a bad release. **When it's the WRONG choice:** Resource-constrained teams, you're running double the infrastructure during the switch, which costs more and isn't justified for low-risk, low-traffic apps.

**Term: Canary Release** **Definition:** Rolling out a new version to a small subset of users first, before a full rollout. **Problem it solves:** Discovering a broken release only after it's already live for 100% of users. **When it's the WRONG choice:** Urgent security patches that need to go out everywhere immediately, canary rollouts intentionally delay full deployment, which works against you in an active incident.

**Term: CI/CD (Continuous Integration/Continuous Deployment)** **Definition:** Automated pipelines that build, test, and deploy code changes continuously and incrementally. **Problem it solves:** Large, infrequent, risky releases where many changes ship at once and failures are hard to isolate. **When it's the WRONG choice:** Rarely wrong to have CI at minimum. Full auto-deploy to production (the CD part) can be premature for early-stage products without solid test coverage, since it ships bugs to users just as fast as fixes.

**Term: IaC (Infrastructure as Code) / Terraform** **Definition:** Defining infrastructure (servers, networks, cloud resources) in code files instead of manual dashboard configuration. **Problem it solves:** Infrastructure drift and undocumented, unrepeatable manual changes made through a cloud console. **When it's the WRONG choice:** Very small, static, single-environment setups where the overhead of writing and maintaining Terraform code exceeds the benefit of a couple of manually configured resources.

## Cloud and Infrastructure

**Term: Cloud Native** **Definition:** Software architected specifically to take advantage of cloud capabilities: containers, elastic scaling, managed services. **Problem it solves:** "Lift and shift" apps that run in the cloud but weren't designed for it, missing out on scalability and resilience benefits. **When it's the WRONG choice:** Apps with hard data residency or latency requirements tied to specific on-prem hardware, or businesses not ready for the operational shift cloud-native patterns require.

**Term: EKS/GKE/AKS** **Definition:** Managed Kubernetes offerings from AWS, Google Cloud, and Microsoft Azure that handle the Kubernetes control plane for you. **Problem it solves:** Running and maintaining your own Kubernetes control plane, which is complex and failure-prone to self-manage. **When it's the WRONG choice:** Teams not already committed to Kubernetes at all, if you don't need K8s's flexibility, a simpler managed container service (like Fargate or Cloud Run) is less operational overhead.

**Term: ECS / Fargate** **Definition:** ECS is Amazon's container orchestration service. Fargate is its serverless mode, where you don't manage the underlying servers at all. **Problem it solves:** Needing container orchestration without the complexity of running Kubernetes yourself. **When it's the WRONG choice:** Teams wanting Kubernetes portability across clouds, ECS locks you into AWS in a way K8s doesn't.

**Term: Edge Computing** **Definition:** Running code physically closer to end users, at distributed "edge" locations, instead of one central data center. **Problem it solves:** High latency for geographically distant users hitting one central server. **When it's the WRONG choice:** Workloads needing heavy compute or centralized, consistent state, edge locations are limited in resources and better suited for lightweight, fast operations.

**Term: CDN (Content Delivery Network)** **Definition:** A distributed network of servers that cache and serve content from locations close to the end user. **Problem it solves:** Slow load times for users far from your origin server. **When it's the WRONG choice:** Highly dynamic, personalized, non-cacheable content, a CDN's main value is caching, it doesn't help much if nothing can be cached.

## Data

**Term: ETL (Extract, Transform, Load)** **Definition:** A process for pulling data from a source, reshaping it, and loading it into a destination system, typically for analytics. **Problem it solves:** Raw data living in scattered, inconsistent formats across systems, unusable for reporting or analysis as-is. **When it's the WRONG choice:** Real-time use cases needing instant data availability, traditional batch ETL introduces delay, ELT or streaming pipelines fit better there.

**Term: Cache Layer / Redis** **Definition:** A fast, temporary storage layer (Redis being the most common tool) that holds frequently accessed data to avoid repeated slow lookups. **Problem it solves:** Hitting the database repeatedly for the same data, adding unnecessary load and latency. **When it's the WRONG choice:** Data that must always be perfectly current, caching introduces the risk of serving stale data, don't cache values where staleness is unacceptable (like real-time account balances).

**Term: ORM (Object-Relational Mapping)** **Definition:** A tool that lets developers interact with a database using their programming language's objects instead of writing raw SQL. **Problem it solves:** Repetitive, error-prone raw SQL scattered throughout application code. **When it's the WRONG choice:** Complex, performance-critical queries, ORMs often generate inefficient SQL under the hood, and hand-written queries give you more control when performance matters most.

**Term: Database Sharding** **Definition:** Splitting a large database into smaller, separate pieces distributed across multiple servers. **Problem it solves:** A single database server hitting storage or performance limits it can't scale past vertically. **When it's the WRONG choice:** Before you actually need it. Sharding adds significant complexity (cross-shard queries, rebalancing), most apps should exhaust simpler scaling options (indexing, read replicas, caching) first.

## Observability

**Term: Distributed Tracing** **Definition:** Tracking a single request as it moves across multiple services, showing exactly where time was spent or where it failed. **Problem it solves:** Not being able to tell which service caused a slowdown or error in a multi-service request chain. **When it's the WRONG choice:** Single-service, monolithic apps, there's no "distributed" path to trace, standard logging and profiling cover it.

**Term: Observability** **Definition:** The broader capability to understand internal system state from external outputs: logs, metrics, and traces combined. **Problem it solves:** Knowing a system is "up" but not why it's slow, erroring, or behaving unexpectedly. **When it's the WRONG choice:** N/A as a goal, the wrong move is under-investing in it and only realizing the gap during an incident.

**Term: Prometheus / Grafana** **Definition:** Prometheus collects and stores time-series metrics. Grafana visualizes those metrics in dashboards. **Problem it solves:** No structured way to track system health trends over time or spot anomalies visually. **When it's the WRONG choice:** Very small setups where a cloud provider's built-in monitoring already covers your needs, running your own Prometheus stack is added operational work.

**Term: ELK Stack (Elasticsearch, Logstash, Kibana)** **Definition:** A toolset for collecting (Logstash), storing/searching (Elasticsearch), and visualizing (Kibana) log data at scale. **Problem it solves:** Logs scattered across many servers with no central place to search or analyze them. **When it's the WRONG choice:** Small-scale apps with low log volume, ELK is resource-heavy to run and maintain, a managed logging service is often simpler.

## Mobile-Specific

**Term: iOS/Android SDK** **Definition:** The official development toolkits provided by Apple and Google for building native apps on their platforms. **Problem it solves:** Building apps without access to platform-specific APIs (camera, notifications, sensors, etc). **When it's the WRONG choice:** When you're building cross-platform and want to avoid maintaining two separate native codebases, a cross-platform framework fits better.

**Term: React Native / Flutter** **Definition:** Frameworks that let developers write one codebase and deploy to both iOS and Android. **Problem it solves:** Building and maintaining two entirely separate native codebases for the same app. **When it's the WRONG choice:** Apps needing deep platform-specific performance or the latest native APIs immediately on release, cross-platform frameworks can lag behind native SDKs.

**Term: Push Notifications** **Definition:** Messages delivered to a user's device even when the app isn't actively open. **Problem it solves:** No way to re-engage or alert users without them having the app open and checking manually. **When it's the WRONG choice:** Overusing it for non-critical updates, this is a product/trust decision more than a technical one, excessive notifications drive uninstalls.

**Term: Offline-first** **Definition:** Designing an app to function without an internet connection, syncing data once connectivity returns. **Problem it solves:** Apps becoming unusable the moment a user loses signal or connectivity. **When it's the WRONG choice:** Apps that inherently require live data (like real-time trading or ride-hailing), offline mode there would show stale or misleading information.

**Term: Deep Linking** **Definition:** A link that opens a specific screen inside an app, rather than just launching it to the home screen. **Problem it solves:** Users landing on a generic app home screen after clicking a link meant for specific content, adding friction. **When it's the WRONG choice:** N/A as a concept, it's low-risk to implement. The main pitfall is not handling the case where the app isn't installed yet.

**Term: App Store Optimization (ASO)** **Definition:** Improving an app's visibility and conversion rate in app store search results. **Problem it solves:** A good app going undiscovered because it doesn't rank or convert well in store search. **When it's the WRONG choice:** Internal or enterprise-only apps not distributed through public app stores, ASO doesn't apply there.

**Term: MDM (Mobile Device Management)** **Definition:** Tools that let organizations secure, monitor, and manage employee mobile devices. **Problem it solves:** Lost or stolen devices, unmanaged BYOD access to company data, and inconsistent security policies across employee phones. **When it's the WRONG choice:** Consumer-facing apps, MDM is for managing an organization's own fleet of devices, not something you'd impose on your app's general user base.
