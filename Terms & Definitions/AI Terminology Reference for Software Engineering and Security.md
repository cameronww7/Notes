# AI Terminology Reference for Software Engineering and Security

---
## 1. Model and Inference Fundamentals

**Term:** Large Language Model (LLM) **Definition:** A neural network trained on large text corpora to predict the next token, which produces general language and reasoning capability as a side effect. **Problem it solves:** Tasks with fuzzy inputs and no deterministic rule set: summarization, classification of unstructured text, code generation, triage of noisy signals. **When it's the WRONG choice:** Anything requiring exact arithmetic, guaranteed reproducibility, auditable decision logic, or sub-100ms latency at high volume. If a regex, a lookup table, or a rules engine solves it, use that instead.

**Term:** Transformer **Definition:** The architecture underlying nearly all modern LLMs, built on self-attention layers that let every token weigh every other token in the input. **Problem it solves:** Long-range dependency modeling with parallel training, which is why models scaled past RNN limits. **When it's the WRONG choice:** As a talking point. Architecture rarely matters to an AppSec decision. Knowing that attention is quadratic in sequence length matters, because it explains context cost and latency.

**Term:** Token **Definition:** The unit a model actually processes, roughly 3 to 4 characters of English text. Code and non-Latin scripts tokenize less efficiently. **Problem it solves:** Gives you the real unit of cost, latency, and context accounting. Every budget and rate limit is denominated in tokens. **When it's the WRONG choice:** Reasoning in "words" or "characters" when estimating cost. Base64 blobs, minified JS, and JSON logs tokenize badly and blow budgets you estimated in characters.

**Term:** Parameters (weights) **Definition:** The learned numeric values in the model. Parameter count is a rough proxy for capability and a direct driver of memory footprint. **Problem it solves:** Capacity planning. A 70B parameter model at 16-bit precision needs roughly 140GB of memory just to hold weights. **When it's the WRONG choice:** As a capability ranking. Post-training quality, reasoning training, and harness design now matter more than raw size. A well-trained 30B beats a poorly trained 200B on most real tasks.

**Term:** Context window **Definition:** The maximum number of tokens the model can attend to in a single request, covering system prompt, conversation, retrieved documents, tool schemas, and tool results. **Problem it solves:** Sets the hard ceiling on how much task-relevant material you can put in front of the model without retrieval. **When it's the WRONG choice:** Treating a large window as a substitute for retrieval or state management. Recall degrades in the middle of long contexts, cost scales linearly, and latency climbs. A 1M-token window is not an excuse to skip document selection.

**Term:** Inference **Definition:** Running a trained model to produce output. Distinct from training, and where nearly all of your production cost and risk lives. **Problem it solves:** Separates the fixed cost of building a model from the variable cost of using one. Your threat model concentrates here. **When it's the WRONG choice:** Focusing security effort on training pipelines you do not own while leaving inference-time inputs, tool permissions, and outputs unmonitored.

**Term:** Temperature and top-p **Definition:** Sampling parameters controlling output randomness. Temperature scales the probability distribution; top-p truncates it to the smallest set of tokens covering probability mass p. **Problem it solves:** Trades determinism for diversity. Low values for extraction, classification, and code. Higher values for brainstorming and content variation. **When it's the WRONG choice:** Expecting temperature 0 to give you determinism. It reduces variance but does not eliminate it. Batching, hardware, and provider-side changes still shift output.

**Term:** Logprobs **Definition:** The log probability the model assigned to each output token, exposed by some APIs. **Problem it solves:** The only cheap, model-native confidence signal available. Useful for flagging low-confidence classifications for human review and for detecting when a model is guessing. **When it's the WRONG choice:** Treating logprobs as calibrated confidence. Models are frequently confidently wrong, and reasoning models often do not expose them at all.

**Term:** Quantization **Definition:** Reducing the numeric precision of model weights (FP16 to INT8 or INT4) to shrink memory and speed up inference. **Problem it solves:** Running capable models on constrained hardware and cutting self-hosted serving cost, usually with modest quality loss. **When it's the WRONG choice:** Precision-sensitive work such as code generation, math, and long multi-step agent loops, where small degradations compound across steps. Also a bad idea when you cannot verify the provenance of the quantized artifact.

**Term:** Distillation **Definition:** Training a smaller model on the outputs of a larger one to transfer capability at lower serving cost. **Problem it solves:** Getting near-frontier quality on a narrow task at a fraction of the price and latency. **When it's the WRONG choice:** Broad or open-ended tasks. Distilled models inherit the teacher's blind spots and generalize poorly outside the distilled distribution. Also frequently a licence violation when distilling a commercial model.

**Term:** Mixture of Experts (MoE) **Definition:** An architecture where a router activates only a subset of specialized subnetworks per token, so total parameters far exceed active parameters. **Problem it solves:** Large model capability at the inference cost of a much smaller one. **When it's the WRONG choice:** Memory-constrained self-hosting. You still need to hold all experts in memory even though you only compute a fraction per token.

**Term:** Embedding **Definition:** A dense vector representation of text, code, or images where semantic similarity maps to geometric proximity. **Problem it solves:** Semantic search, clustering, deduplication, and similarity matching where keyword search fails. **When it's the WRONG choice:** Exact-match, identifier, or rare-token lookup. Embeddings are poor at finding a specific CVE number, hash, or error code. Use lexical search or hybrid retrieval.

**Term:** Vector database **Definition:** A store optimized for approximate nearest-neighbor search over embeddings, usually with metadata filtering. **Problem it solves:** Fast similarity search at scale with per-record filtering. **When it's the WRONG choice:** Small corpora, where a numpy array or pgvector in your existing Postgres is simpler and cheaper. Adding a new stateful datastore for 50,000 chunks is unjustified operational surface.

**Term:** Multimodal model **Definition:** A model accepting or producing more than one modality: text, images, audio, video. **Problem it solves:** Screenshot analysis, document and diagram understanding, OCR-free extraction, UI automation. **When it's the WRONG choice:** Structured data you already have in text form. Also a real security concern: images are an unmonitored injection channel, since most prompt-injection filters only inspect text.

**Term:** Reasoning model **Definition:** A model post-trained to generate extended intermediate reasoning before its final answer, spending more compute at inference time. **Problem it solves:** Multi-step problems where accuracy matters more than latency: threat modeling, root cause analysis, complex refactors, ambiguous triage. **When it's the WRONG choice:** Latency-sensitive, high-volume, or simple tasks. You pay for reasoning tokens on every call. Classification and extraction do not benefit and get 5 to 20x more expensive.

**Term:** Test-time compute **Definition:** Spending more inference compute per query (longer reasoning, sampling multiple candidates, self-verification) to improve accuracy without retraining. **Problem it solves:** A quality dial you can turn per request instead of per model. **When it's the WRONG choice:** As a fix for missing context or a bad prompt. More thinking about the wrong inputs produces a more elaborate wrong answer.

**Term:** KV cache **Definition:** Cached key and value tensors from prior tokens so the model does not recompute attention over the whole sequence for each new token. **Problem it solves:** Makes long-context generation tractable. Directly explains why prompt prefixes should be stable. **When it's the WRONG choice:** Ignoring it when designing prompts. Putting variable content early in the prompt invalidates the cache and multiplies cost and latency for no benefit.

**Term:** Small Language Model (SLM) **Definition:** A compact model, roughly 1B to 15B parameters, runnable on a single GPU or a laptop. **Problem it solves:** On-prem, air-gapped, edge, and high-volume narrow tasks where data cannot leave the boundary or per-call cost dominates. **When it's the WRONG choice:** Open-ended reasoning, long agent loops, or anything needing broad world knowledge. SLMs hallucinate more and fall apart on multi-step tool use.

**Term:** Frontier model **Definition:** The current top-capability models from major labs, typically the reference point for what is technically possible right now. **Problem it solves:** Setting the ceiling for feasibility assessment. If the frontier cannot do it reliably, your fine-tuned 8B will not either. **When it's the WRONG choice:** As a default production dependency for every workload. Most tasks in a real system are cheap classification and extraction that a mid-tier model handles at a tenth the cost.

## 2. Prompting and Context

**Term:** Prompt engineering **Definition:** Structuring instructions, examples, and output format specifications to make model behavior reliable. **Problem it solves:** Large accuracy gains at zero training cost. Usually the highest-leverage first move on any AI task. **When it's the WRONG choice:** When the model lacks the necessary knowledge or the task needs a behavior change no instruction achieves. At that point you need retrieval or fine-tuning, and more prompt iteration is wasted effort.

**Term:** System prompt **Definition:** Instructions positioned with elevated priority that establish role, constraints, output format, and available tools. **Problem it solves:** Persistent behavior across turns without repeating instructions. **When it's the WRONG choice:** As a security control. A system prompt is a strong suggestion, not a boundary. Anything that must not happen needs enforcement outside the model, and assume the contents will leak (OWASP LLM07).

**Term:** Few-shot prompting **Definition:** Including labeled input/output examples in the prompt to demonstrate the target behavior. **Problem it solves:** Format compliance and edge-case handling without fine-tuning. Often closes most of the gap to a tuned model. **When it's the WRONG choice:** When you have hundreds of examples worth using. At that scale examples eat context on every call, and fine-tuning or a distilled model is cheaper. Also risky when examples contain real customer data.

**Term:** Chain of thought (CoT) **Definition:** Prompting the model to produce intermediate reasoning steps before its conclusion. **Problem it solves:** Improves accuracy on multi-step logic and gives you a reviewable trace of how the model got there. **When it's the WRONG choice:** Treating the trace as a faithful account of the model's actual computation. It is generated text, not an audit log, and it can be plausible while the underlying process was different. Also unnecessary overhead on reasoning models that already do it internally.

**Term:** Context engineering **Definition:** The discipline of deciding what information occupies the context window at each step: retrieval, tool schemas, memory, compaction, and pruning. **Problem it solves:** The dominant failure mode in agent systems. Most agent failures are context failures, not model failures. **When it's the WRONG choice:** Single-turn, single-purpose calls. Building a context management layer for a classification endpoint is architecture for its own sake.

**Term:** Context rot **Definition:** Degradation of model performance as the context window fills with stale, irrelevant, or contradictory material. **Problem it solves:** Naming it explains why long agent sessions get worse over time and justifies compaction, subagents, and session resets. **When it's the WRONG choice:** As the diagnosis for every failure. Sometimes the model simply cannot do the task, and no amount of context hygiene fixes that.

**Term:** Structured output **Definition:** Forcing the model to emit output conforming to a schema, either via constrained decoding or a JSON mode. **Problem it solves:** Removes brittle output parsing and makes model responses safe to feed into downstream code. **When it's the WRONG choice:** Open-ended reasoning and analysis, where rigid schemas measurably degrade quality. Also note that schema conformance guarantees shape, not truthfulness. You still validate values.

**Term:** Prompt caching **Definition:** Provider-side caching of a stable prompt prefix so repeated calls skip recomputation, usually at a large discount. **Problem it solves:** Big cost and latency reduction for agents and RAG systems that resend the same system prompt and tool definitions on every turn. **When it's the WRONG choice:** Prompts with early variable content, where nothing caches. Also a subtle multi-tenant concern: verify cache scoping so one tenant's cached prefix is never reachable by another.

## 3. Retrieval and Knowledge

**Term:** Retrieval-Augmented Generation (RAG) **Definition:** Retrieving relevant documents at query time and injecting them into the prompt so the model answers from supplied evidence. **Problem it solves:** Current, proprietary, and citable knowledge without retraining. Also the cheapest way to reduce hallucination on domain content. **When it's the WRONG choice:** Teaching the model a new style, format, or behavior; that is fine-tuning territory. Also inappropriate when the corpus is small enough to fit in context, and dangerous when the corpus is not access-controlled per user, which is how RAG becomes a data leak.

**Term:** Chunking **Definition:** Splitting documents into retrievable segments, ideally along semantic or structural boundaries. **Problem it solves:** Retrieval granularity. Whole documents waste context; over-small chunks lose the context needed to interpret them. **When it's the WRONG choice:** Fixed-size character splitting on structured content such as code, tables, or config files, where it severs meaning mid-construct and destroys retrieval quality.

**Term:** Reranking **Definition:** A second-stage model that reorders initial retrieval candidates by relevance to the query. **Problem it solves:** Vector search returns loosely related results; reranking fixes precision at the top, which is what actually lands in context. **When it's the WRONG choice:** Latency-critical paths, since it adds a full model call. Also pointless if your first-stage recall is bad; reranking cannot surface a document retrieval never returned.

**Term:** Hybrid search **Definition:** Combining lexical search (BM25) with vector search and fusing the rankings. **Problem it solves:** Covers both semantic paraphrase and exact-token queries. In security corpora this matters constantly: CVE IDs, function names, error strings. **When it's the WRONG choice:** Purely conceptual corpora with no identifiers, where the added complexity of two indexes and a fusion step buys little.

**Term:** GraphRAG **Definition:** Retrieval over a knowledge graph of extracted entities and relationships rather than over flat text chunks. **Problem it solves:** Multi-hop questions that require connecting facts scattered across documents, which flat chunk retrieval handles badly. **When it's the WRONG choice:** Most cases. Graph construction is expensive, brittle, and needs ongoing maintenance. Fix your chunking and reranking before reaching for a graph.

**Term:** Semantic cache **Definition:** Caching responses keyed by embedding similarity so near-duplicate queries return a stored answer. **Problem it solves:** Large cost savings on repetitive workloads such as support bots and internal Q&A. **When it's the WRONG choice:** Anything where the answer depends on user identity, permissions, or time. Semantic caching without tenant scoping is a cross-tenant data disclosure waiting to happen, and "similar" queries can have genuinely different correct answers.

## 4. Training and Adaptation

**Term:** Pretraining **Definition:** The initial large-scale self-supervised training run that produces a base model. **Problem it solves:** Builds general language, code, and world knowledge. Only relevant to you as the source of the model's knowledge cutoff and its training-data provenance risk. **When it's the WRONG choice:** Never something an enterprise team should be doing. If someone proposes pretraining a model from scratch to solve a business problem, that is a red flag.

**Term:** Fine-tuning (SFT) **Definition:** Continued supervised training on curated input/output pairs to specialize a model's behavior. **Problem it solves:** Consistent tone, output format, domain-specific style, and latency reduction by moving a narrow task to a smaller model. **When it's the WRONG choice:** Injecting facts. Fine-tuning teaches behavior, not knowledge, and fine-tuned facts go stale and cannot be cited. It also creates a versioned artifact you now have to secure, evaluate, and maintain forever. Try prompting and RAG first.

**Term:** LoRA / PEFT **Definition:** Parameter-efficient fine-tuning that trains small low-rank adapter matrices instead of updating all weights. **Problem it solves:** Fine-tuning on modest hardware, and the ability to hot-swap task-specific adapters over one base model. **When it's the WRONG choice:** Large behavioral shifts or new capabilities, where limited adapter capacity is not enough. Also a supply chain concern: an adapter is an unsigned executable behavior change, and adapter provenance is rarely tracked.

**Term:** RLHF **Definition:** Reinforcement learning from human feedback, where a reward model trained on human preference rankings is used to tune model behavior. **Problem it solves:** Turns a raw next-token predictor into something that follows instructions and refuses harmful requests. **When it's the WRONG choice:** As an enterprise technique. It requires a preference dataset, a reward model, and RL infrastructure. Also worth understanding as a limitation: RLHF optimizes for what raters preferred, which produces sycophancy and confident-sounding wrong answers.

**Term:** RLVR **Definition:** Reinforcement learning from verifiable rewards, training against programmatically checkable outcomes such as passing tests or correct math. **Problem it solves:** Removes the human rater bottleneck and drove most of the recent gains in coding and reasoning models. **When it's the WRONG choice:** Subjective domains with no automatic verifier. Also creates measurable reward hacking: models learn to pass the test rather than solve the problem, which shows up as code that games assertions.

**Term:** Alignment **Definition:** The general project of making model behavior match intended values and instructions. **Problem it solves:** Baseline refusal behavior and instruction-following that make a model deployable at all. **When it's the WRONG choice:** As a control you rely on. Alignment is probabilistic and adversarially defeatable. A well-aligned model is a safer default, not a security boundary.

**Term:** Catastrophic forgetting **Definition:** Loss of previously learned general capability when a model is fine-tuned narrowly on new data. **Problem it solves:** Explains why a tuned model gets better at your task and worse at everything else, including its safety behavior. **When it's the WRONG choice:** Overlooking it. Fine-tuning has been shown to degrade safety training even with benign data, so any tuned model needs its own safety eval, not the base model's.

**Term:** Synthetic data **Definition:** Model-generated training or evaluation data, often filtered and verified before use. **Problem it solves:** Scarce labeled data, privacy-constrained domains, and generating edge cases that rarely occur naturally. **When it's the WRONG choice:** As a substitute for real distribution coverage. Synthetic data inherits the generator's biases and blind spots, and unfiltered recursive use degrades quality (model collapse). Never validate a system exclusively on synthetic evals.

## 5. Agents, Tools, and Protocols

**Term:** Agent **Definition:** A system where a model runs in a loop, choosing actions and calling tools to pursue a goal, with control over its own next step. **Problem it solves:** Multi-step tasks where the required sequence is not known in advance: investigation, remediation, triage across systems. **When it's the WRONG choice:** Deterministic workflows. If you can draw the flowchart, write the workflow. An agent adds nondeterminism, cost, latency, and a large new attack surface to solve something a DAG solves better.

**Term:** Tool use (function calling) **Definition:** The model emitting a structured request to invoke a named function with arguments, which your code executes and returns. **Problem it solves:** Connects a text generator to real actions and real data: queries, API calls, code execution. **When it's the WRONG choice:** Handing over more capability than the task needs. Every tool is a permission grant. A read-only tool that accepts a raw query string is effectively a database exfiltration primitive.

**Term:** Subagent **Definition:** A delegated agent with its own context window, system prompt, and tool subset, which returns a condensed result to the orchestrator. **Problem it solves:** Context isolation. The subagent can burn 50,000 tokens exploring and return 1,500, keeping the main context clean. **When it's the WRONG choice:** Tasks needing tight back-and-forth with the parent, since the interface is a lossy natural-language handoff. Also when the coordination overhead exceeds the work, which is the standard multi-agent over-engineering failure.

**Term:** Agent Skill **Definition:** A packaged, lazily loaded instruction set (typically a folder with a markdown file plus optional scripts) that an agent loads only when the task matches. **Problem it solves:** Reusable procedural expertise without permanent context cost. Encoding your organization's actual review process rather than re-prompting it. **When it's the WRONG choice:** When you need a capability rather than instructions. Skills carry knowledge; tools and MCP servers grant access. A skill also becomes a supply chain artifact the moment it contains scripts, so treat third-party skills as code.

**Term:** Model Context Protocol (MCP) **Definition:** An open protocol standardizing how AI clients discover and invoke tools, resources, and prompts exposed by servers. **Problem it solves:** Eliminates N-by-M custom integrations. One MCP server serves any compliant client. **When it's the WRONG choice:** A single integration you control end to end, where a direct function call is simpler. Bigger caution: MCP is now a primary attack surface. Third-party servers should be treated as untrusted code, tool schemas pinned and signed, and description drift alerted on. Unit 42 measured a 78% attack success rate against agents with five connected servers.

**Term:** A2A (Agent-to-Agent) **Definition:** A protocol for agents to advertise capabilities and delegate tasks to other agents across organizational boundaries. **Problem it solves:** Interoperability between independently built and operated agents. **When it's the WRONG choice:** Inside a single system, where in-process delegation is far simpler. It also creates trust delegation chains that most identity infrastructure cannot currently express or audit (OWASP ASI07).

**Term:** ReAct **Definition:** The reason-then-act loop pattern: the model reasons about state, calls a tool, observes the result, and repeats. **Problem it solves:** The foundational agent control loop. Still the default for most tool-using agents. **When it's the WRONG choice:** Long horizons, where errors compound and the loop wanders. Beyond roughly 10 to 15 steps you need explicit planning, checkpoints, or subagent decomposition.

**Term:** Orchestration **Definition:** The coordination layer routing work among models, tools, and subagents, handling retries, state, and error recovery. **Problem it solves:** Reliability. This is where your production robustness actually lives, not in the model. **When it's the WRONG choice:** Adopting a heavy orchestration framework for a two-step flow. Framework abstraction is the leading cause of undebuggable agent systems.

**Term:** Agent harness **Definition:** The scaffolding around the model: system prompt, tool definitions, loop control, context management, permission gates, and sandbox. **Problem it solves:** Nearly all of the observed capability difference between "this agent works" and "this agent flails" on the same model. **When it's the WRONG choice:** Building your own when an existing harness fits. But recognize that harness configuration is now a security control surface, and it belongs in code review.

**Term:** Computer use **Definition:** An agent operating a GUI directly through screenshots and synthesized mouse and keyboard input. **Problem it solves:** Automating systems with no API: legacy internal apps, vendor portals, thick clients. **When it's the WRONG choice:** Anything with an API. It is slow, brittle, expensive, and it inherits the full session privileges of whatever desktop it runs on. Screenshots are also an injection channel most filters never inspect.

**Term:** Agent memory **Definition:** State persisted across turns or sessions, spanning short-term conversation, retrieved episodic history, and long-term learned facts. **Problem it solves:** Continuity, so the agent does not restart from zero every session. **When it's the WRONG choice:** Persistent memory on by default. It is a poisoning target (OWASP ASI, memory poisoning), it crosses tenant and session boundaries if unscoped, and stale memory silently corrupts later reasoning. Scope memory per task, and never treat memory content as trusted input.

**Term:** Human in the loop (HITL) **Definition:** Requiring human approval before an agent executes a defined class of action. **Problem it solves:** The only reliable control on high-impact agent actions today: writes, deploys, financial transactions, permission changes. **When it's the WRONG choice:** High-frequency, low-impact operations, where approval fatigue makes humans rubber-stamp everything and the control becomes theater. Gate on impact, not on volume.

**Term:** Least agency **Definition:** The principle, introduced in the OWASP Agentic Top 10, of granting an agent only the minimum autonomy the task requires, distinct from least privilege on data. **Problem it solves:** Directly addresses excessive agency, the risk that gets people breached. Constrains the number of steps an agent can take unsupervised, not just what data it can read. **When it's the WRONG choice:** As a substitute for least privilege rather than an addition to it. You need both: bounded autonomy and scoped credentials.

**Term:** Sandboxing / blast radius isolation **Definition:** Running agent-executed code and tool calls in an isolated environment with constrained filesystem, network, and credential access. **Problem it solves:** The only durable control against agent-driven code execution. Contains the damage when injection succeeds, and you should assume it will. **When it's the WRONG choice:** As your only control. Sandboxing limits impact but does nothing about exfiltration through the agent's legitimate output channel, which is how most real AI data loss happens.

## 6. Evaluation and Reliability

**Term:** Eval **Definition:** A repeatable test suite measuring model or agent output quality against defined criteria on a fixed dataset. **Problem it solves:** The difference between engineering and vibes. Without evals you cannot tell whether a prompt change, model upgrade, or new guardrail improved or regressed anything. **When it's the WRONG choice:** Never wrong to have. It is wrong to build an elaborate eval framework before you have 20 real failure cases. Start from actual production failures.

**Term:** LLM as judge **Definition:** Using a model to score another model's output against a rubric. **Problem it solves:** Scales evaluation of subjective qualities that no deterministic assertion can check. **When it's the WRONG choice:** Anything programmatically verifiable, where an assertion is cheaper and correct. Judges also carry known biases toward length, verbosity, and their own family's output style, and they must be validated against human labels before you trust them.

**Term:** Benchmark contamination **Definition:** Benchmark data appearing in training data, inflating reported scores without real capability gain. **Problem it solves:** Explains why public benchmark leaderboards correlate weakly with performance on your workload. **When it's the WRONG choice:** Selecting a model from public benchmarks. Build a private eval set from your own data. That is the only number that predicts your outcome.

**Term:** Hallucination **Definition:** Confident generation of false content, including invented APIs, citations, CVEs, package names, and configuration flags. **Problem it solves:** Naming a structural property, not a bug. It comes from the same mechanism as useful generation and cannot be eliminated, only constrained. **When it's the WRONG choice:** Assuming grounding solves it. RAG reduces hallucination on retrieved content and does nothing about fabricated reasoning over that content. Verification stays your job.

**Term:** Grounding **Definition:** Constraining output to supplied source material with traceable citations. **Problem it solves:** Makes output auditable, which is what turns an AI answer into something usable in a compliance or IR context. **When it's the WRONG choice:** Creative, analytical, or synthesis tasks where the value is the model connecting things no single source states. Also note that a citation being present does not mean it supports the claim, and models do misattribute.

**Term:** Drift **Definition:** Degradation of system performance over time as inputs, provider models, or the environment change under a fixed configuration. **Problem it solves:** Explains why a working system quietly stops working. Provider-side model updates change behavior without any change on your side. **When it's the WRONG choice:** Assuming pinned model versions eliminate it. Your input distribution drifts too, and pinned versions get deprecated.

**Term:** Observability / tracing **Definition:** Structured capture of every prompt, tool call, tool result, token count, and decision in an agent run, usually as nested spans. **Problem it solves:** The only way to debug nondeterministic multi-step systems, and the only way to do incident response on an agent. Auditors are now asking what an agent touched and when. **When it's the WRONG choice:** Never skip it. But logging raw prompts and completions creates a new sensitive data store containing everything users pasted in, so it needs the same classification, retention, and access control as any PII store.

**Term:** Guardrails **Definition:** Input and output filters evaluating prompts and completions against safety, policy, and content rules before they proceed. **Problem it solves:** Catches the common, known-shape cases: obvious injection patterns, PII in output, off-topic use, toxic content. **When it's the WRONG choice:** As your primary boundary. Guardrails are classifiers with false negative rates, defeated by paraphrase, encoding, and multilingual and multi-turn attacks. They reduce volume; they do not enforce. Authorization enforcement belongs in your application, not in a filter.

## 7. Attacks and Offensive AI Security

**Term:** Prompt injection (direct) **Definition:** Attacker-supplied input that the model interprets as instruction rather than data, overriding its intended task. LLM01 in the OWASP LLM Top 10, and unsolved by design because instructions and data share one channel. **Problem it solves:** For an attacker: control of model behavior with no code execution and no credentials. **When it's the WRONG choice:** As a framing when the real issue is authorization. If the agent should never have had access to the resource, injection was the trigger, not the vulnerability. Fix the permission.

**Term:** Indirect prompt injection **Definition:** Malicious instructions planted in content the model later retrieves: a web page, PDF, email, calendar invite, code comment, RAG document, or MCP tool description. **Problem it solves:** For an attacker: no interaction with the victim required. EchoLeak (CVE-2025-32711) demonstrated zero-click exfiltration through this path. **When it's the WRONG choice:** Treating it as the same problem as direct injection. Direct injection is a misuse question about your own user; indirect injection is an untrusted-data-flow question and needs data flow controls, provenance labeling, and egress restrictions.

**Term:** Jailbreak **Definition:** Input designed to bypass a model's safety training so it produces content it would normally refuse. **Problem it solves:** For an attacker: reputational damage, policy violation, and generation of harmful content through your branded interface. **When it's the WRONG choice:** Prioritizing jailbreak resistance over injection resistance in an enterprise agent. A jailbroken chatbot is embarrassing. An injected agent with write access to production is an incident.

**Term:** Lethal trifecta **Definition:** The dangerous combination of an agent having access to private data, exposure to untrusted content, and an external communication channel. Any two are manageable. All three make exfiltration possible. **Problem it solves:** The single most useful architectural review question for agent designs. If all three are present, no prompt-level mitigation closes it. **When it's the WRONG choice:** As a complete threat model. It captures exfiltration well and says nothing about destructive actions, where a write-capable tool alone is sufficient harm.

**Term:** Data and model poisoning **Definition:** Corrupting training, fine-tuning, or RAG data to implant behavior. LLM04. **Problem it solves:** For an attacker: persistent influence that survives prompt-level defenses. Research has shown small absolute numbers of poisoned documents can be effective regardless of dataset size. **When it's the WRONG choice:** Over-focusing on pretraining poisoning you cannot influence while your own RAG ingestion pipeline accepts unvetted documents. The realistic vector is your corpus, not the foundation model.

**Term:** Backdoored model **Definition:** A model with a hidden trigger that produces attacker-specified behavior on a specific input pattern while behaving normally otherwise. **Problem it solves:** For an attacker: undetectable by standard evaluation, since the trigger is unknown to defenders. **When it's the WRONG choice:** Assuming eval coverage detects it. It will not. The control is provenance: signed weights, verified sources, safetensors over pickle formats, and no arbitrary Hugging Face downloads into production.

**Term:** Model extraction **Definition:** Reconstructing an approximation of a proprietary model by systematically querying it and training on the responses. **Problem it solves:** For an attacker: IP theft, plus a local copy for offline attack development against your production model. **When it's the WRONG choice:** As a top-tier concern for a company consuming models rather than building them. Rate limiting and abuse detection cover the practical exposure.

**Term:** Membership inference **Definition:** Determining whether a specific record was in a model's training data by analyzing its outputs. **Problem it solves:** For an attacker: a privacy violation and a regulatory exposure, since it can confirm an individual's presence in a dataset. **When it's the WRONG choice:** Ignoring it when you fine-tune on customer or employee data. That is precisely where it becomes a GDPR and contractual problem.

**Term:** Adversarial examples **Definition:** Inputs perturbed to cause misclassification, often imperceptibly to humans. **Problem it solves:** For an attacker: evading ML-based detection, including malware classifiers, spam filters, and fraud models. **When it's the WRONG choice:** Applying the classical adversarial-perturbation literature to LLM security. Against text models, semantic attacks like injection are far more practical than gradient-based perturbation.

**Term:** Excessive agency **Definition:** An agent holding more permission, autonomy, or tool capability than its function requires. LLM06, and the amplifier that converts every other AI vulnerability into real impact. **Problem it solves:** For an attacker: an injection is only as damaging as what the agent is allowed to do. Broad permissions are the difference between a weird response and a deleted database. **When it's the WRONG choice:** Treating it as a permissions-only problem. It also covers autonomy: an agent with read-only creds that can take 200 unsupervised steps is still excessive agency.

**Term:** System prompt leakage **Definition:** Extraction of system instructions, revealing tool inventory, internal logic, and sometimes embedded credentials or endpoints. LLM07. **Problem it solves:** For an attacker: reconnaissance that makes subsequent attacks precise instead of blind. **When it's the WRONG choice:** Investing heavily in preventing leakage rather than in making leakage harmless. Assume the prompt is public. Never put secrets or authorization logic in it.

**Term:** Tool poisoning **Definition:** Malicious instructions embedded in an MCP tool's description or schema, which the model reads as trusted instruction during tool selection. **Problem it solves:** For an attacker: injection that never touches user input and is invisible in the conversation. **When it's the WRONG choice:** Assuming input filtering covers it. Tool metadata is not user input. Controls are schema pinning, signing, and drift detection at install and at runtime.

**Term:** Rug pull **Definition:** A tool or MCP server that behaves benignly through approval and review, then changes its description or behavior after trust is established. **Problem it solves:** For an attacker: defeats one-time review, which is how nearly all tool approval works today. **When it's the WRONG choice:** Relying on install-time review alone. The control is continuous verification and alerting on post-approval description drift.

**Term:** Confused deputy **Definition:** An agent with legitimate elevated privilege being induced to perform an action on behalf of a less-privileged attacker, because the system authorizes the agent's identity rather than the requester's. **Problem it solves:** Names the core identity failure in agent architecture, and explains why per-agent identity with delegated, attenuated authority matters more than agent-level RBAC. **When it's the WRONG choice:** As a novel AI concept. It is a decades-old authorization pattern, which is good news: your existing identity and delegation thinking applies directly.

**Term:** Agent goal hijack **Definition:** ASI01 in the OWASP Agentic Top 10. Redirecting an agent's objective or plan through content it reads, while the agent still believes it is serving the user. **Problem it solves:** For an attacker: control over a multi-step plan, not a single response, which compounds impact across the whole task. **When it's the WRONG choice:** Conflating it with prompt injection. Injection is the mechanism; goal hijack is the outcome at the planning layer. Detection requires monitoring goal and plan drift, not just input content.

**Term:** Memory poisoning **Definition:** Planting false or malicious content in an agent's persistent memory so it influences future sessions. **Problem it solves:** For an attacker: persistence. The payload survives session termination, context clearing, and prompt hardening. **When it's the WRONG choice:** Treating memory as internal state. Memory is untrusted input on read, and it needs write validation, provenance, scoping, and expiry.

**Term:** Slopsquatting **Definition:** Registering package names that LLMs commonly hallucinate, so AI-generated install commands pull attacker-controlled code. **Problem it solves:** For an attacker: supply chain compromise that requires no compromise of any real package. The developer's assistant does the work. **When it's the WRONG choice:** Assuming existing SCA covers it. Your scanner validates what is in the lockfile. This attack targets the moment before the lockfile exists, so the control sits at install time and in the IDE.

**Term:** Unbounded consumption **Definition:** LLM10. Uncontrolled resource use through expensive queries, recursive agent loops, or reasoning-token amplification. Also called denial of wallet. **Problem it solves:** For an attacker: financial damage and service degradation without any exploit, just usage. **When it's the WRONG choice:** Treating it as ordinary rate limiting. Request-count limits miss it entirely. You need per-tenant token budgets, step caps on agent loops, and cost anomaly alerting.

**Term:** Vector and embedding weaknesses **Definition:** LLM08. Attacks on the retrieval layer: cross-tenant retrieval from a shared index, embedding inversion recovering source text, and injection through indexed documents. **Problem it solves:** For an attacker: access to data the user was never authorized to see, through a channel most access reviews never examine. **When it's the WRONG choice:** Assuming document-level ACLs in the source system carry into the vector store. They do not unless you propagate them. This is the most common serious flaw in enterprise RAG deployments.

**Term:** Rogue agent **Definition:** An agent operating outside intended constraints, whether through compromise, misalignment, or drift, while still appearing legitimate in logs. **Problem it solves:** For a defender: names the case that behavioral monitoring and kill switches exist to catch, since nothing in the request pattern looks malicious. **When it's the WRONG choice:** Reaching for it before checking whether the agent is simply misconfigured. Most apparent rogue behavior is over-broad permissions plus a bad prompt.

**Term:** Crescendo (multi-turn) attack **Definition:** Escalating across many benign-looking turns to reach a goal that would be refused if requested directly. **Problem it solves:** For an attacker: defeats per-request filtering completely, since every individual message passes. **When it's the WRONG choice:** Building only stateless request-level guardrails. Detection requires session-level and conversation-level analysis.

## 8. Defenses, Tooling, and Governance

**Term:** AI-SPM **Definition:** AI Security Posture Management. Discovery and inventory of AI assets (models, agents, MCP servers, gateways, SDKs) plus configuration and posture assessment. Shaped after CSPM and DSPM. **Problem it solves:** The first real question: what AI do we actually have running. You cannot govern an inventory you do not have. **When it's the WRONG choice:** As an enforcement layer. AI-SPM finds and assesses; it does not sit inline and block. Buying it expecting runtime prevention is a common mismatch.

**Term:** AI gateway **Definition:** An inline proxy between callers and model endpoints that authenticates, applies policy, routes, meters, and audits every request. **Problem it solves:** The single highest-leverage architectural control in an enterprise AI deployment. One enforcement and audit point instead of per-application controls, plus centralized key management and per-tenant budgets. **When it's the WRONG choice:** Where latency budgets are tight and the model call is already on the critical path, or when it becomes a single point of failure without HA. Also do not confuse it with guardrails; guardrails are a feature within the policy step, not the whole gateway.

**Term:** AI red teaming **Definition:** Adversarial testing of AI systems using injection, jailbreak, extraction, and agentic attack techniques, often automated with a probe framework. **Problem it solves:** Finds failures before attackers do, and produces the concrete failure cases your evals and guardrails should be built from. **When it's the WRONG choice:** As a point-in-time compliance exercise. A model or prompt change invalidates the results. It belongs in CI against your eval suite, not in an annual report.

**Term:** AIBOM **Definition:** AI Bill of Materials. Inventory of models, datasets, adapters, agents, tools, and MCP servers with provenance, typically expressed in CycloneDX. **Problem it solves:** Supply chain accountability for AI components, and the emerging expected artifact for AI Act, ISO 42001, and audit readiness. **When it's the WRONG choice:** Generating it as a static document. An AIBOM that is not produced by your build pipeline is stale on arrival, exactly like a hand-maintained SBOM.

**Term:** MLSecOps **Definition:** Extending security practice into the ML and AI lifecycle: data provenance, model scanning, artifact signing, and pipeline controls. **Problem it solves:** Puts model artifacts under the same supply chain discipline as code. Scanning model files for deserialization payloads belongs here. **When it's the WRONG choice:** As the primary program frame for an organization that consumes APIs rather than trains models. Your risk is at inference, agents, and tool permissions, not in training pipelines you do not run.

**Term:** Shadow AI **Definition:** Unsanctioned AI tool and agent usage: consumer accounts, unreviewed IDE assistants, and MCP servers installed on developer laptops. **Problem it solves:** Names the largest practical enterprise AI data exposure today. Source code, credentials, and customer data pasted into unreviewed tools. **When it's the WRONG choice:** Responding with a blanket ban. Prohibition drives usage further underground. Sanctioned, gateway-fronted alternatives plus egress visibility work; policy documents do not.

**Term:** Non-Human Identity (NHI) for agents **Definition:** Treating agents as first-class principals with their own scoped, short-lived credentials and auditable delegation chains, rather than reusing service accounts or human tokens. **Problem it solves:** Attribution and blast radius. Answers who the agent was acting for and what it was authorized to do, which shared service accounts make impossible. **When it's the WRONG choice:** Using traditional IAM patterns unchanged. Agents create ephemeral, high-volume, cross-service credential use that human-oriented lifecycle and review processes cannot keep up with.

**Term:** MITRE ATLAS **Definition:** An adversarial tactics and techniques knowledge base for AI systems, structured like MITRE ATT&CK. **Problem it solves:** Gives you an attack-path vocabulary for threat modeling AI systems and mapping detection coverage. **When it's the WRONG choice:** As a prioritized risk list. It is a technique catalog, not a top-10. Use OWASP's lists for prioritization and ATLAS for coverage mapping.

**Term:** AIVSS **Definition:** AI Vulnerability Scoring System. A scoring framework for AI and agentic vulnerabilities, which CVSS handles poorly because it has no notion of autonomy or agency. **Problem it solves:** Lets you rank agentic findings on something better than a CVSS score that ignores whether the component can take autonomous action. **When it's the WRONG choice:** As a replacement for CVSS across the board, or as a mature standard. It is early, and adoption in tooling is thin.

**Term:** OWASP LLM Top 10 / Agentic Top 10 / MCP Top 10 **Definition:** Three layered OWASP lists. The LLM Top 10 (LLM01 to LLM10) covers model-level risk. The Agentic Top 10 (ASI01 to ASI10, 2026) covers autonomy, delegation, memory, and inter-agent risk. The MCP Top 10 covers the tool-connection layer. **Problem it solves:** Shared vocabulary for AI risk conversations, an architecture review checklist, and increasingly what auditors reference for AI-enabled systems under SOC 2 and FedRAMP. **When it's the WRONG choice:** Using the LLM Top 10 for an agentic system. It treats the model as input-to-output and misses the entire class of risk that appears when the model becomes an actor with credentials and memory. Match the list to the architecture.

**Term:** NIST AI RMF **Definition:** A voluntary risk management framework structured around Govern, Map, Measure, Manage functions for AI systems. **Problem it solves:** Gives governance and risk teams a recognized structure, and a defensible answer for how you prioritize AI risk. **When it's the WRONG choice:** As technical guidance. It will not tell an engineer how to prevent injection. Pair it with OWASP for implementation.

**Term:** ISO/IEC 42001 **Definition:** A certifiable management system standard for AI, comparable in shape to 27001. **Problem it solves:** Third-party attestable AI governance, which increasingly appears in enterprise procurement and customer security reviews. **When it's the WRONG choice:** As evidence of technical security. Like any management system certification, it evidences process, not that your agents are hardened.

**Term:** EU AI Act **Definition:** Risk-tiered EU regulation imposing obligations by system risk classification, with the heaviest requirements on high-risk uses and general-purpose model providers. **Problem it solves:** Forces documented classification, transparency, and human oversight for AI systems in scope. **When it's the WRONG choice:** Treating it as a security standard, or assuming a non-EU footprint exempts you. Scope follows the market where output is used, and obligations are phasing in on separate timelines. Verify current dates rather than working from a summary.

**Term:** Differential privacy **Definition:** Adding calibrated noise so no individual record measurably influences an output, with a formal privacy budget. **Problem it solves:** Mathematically bounded privacy guarantees when training or analyzing sensitive data, including against membership inference. **When it's the WRONG choice:** Small datasets or high-accuracy requirements, where the noise needed for a meaningful epsilon destroys utility. Also irrelevant to inference-time data leakage, which is where most real exposure sits.

**Term:** Confidential computing for inference **Definition:** Running model inference inside hardware-backed trusted execution environments so prompts and weights are not visible to the host. **Problem it solves:** Lets regulated workloads use hosted inference with a cryptographic rather than contractual assurance about the provider. **When it's the WRONG choice:** As a general default. It costs performance, narrows model and region availability, and does nothing about the risks that dominate in practice: injection, over-permissioned agents, and data exfiltration through legitimate output channels.
